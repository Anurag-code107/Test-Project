# Step 10: test-strategy

## Goal
Map integration test scenarios systematically — extract from the spec design under construction so that step 13 can populate the Acceptance Tests pointer and step 14 can describe fixture requirements correctly.

## Inputs (from prior steps)
- All findings so far (FRs, scope, security, events)

## Loads (just-in-time)
- None (analysis-only step; uses already-loaded context)

## Procedure

### 1. BE integration test extraction (8-bullet checklist)

Walk through the design under construction. For each, extract specific test scenarios:

1. **Entity relationships** — for each parent-child or cross-entity relationship: cascade behavior (delete parent → child handling), referential integrity, ordering constraints.
2. **State machine transitions** — for each entity with status: every valid transition end-to-end (e.g., DRAFT→PUBLISHED→ARCHIVED), invalid transitions return correct error. Test full lifecycle.
3. **Business rules** — for each validation in service layer (e.g., "can't publish with 0 lessons"), enforce against real DB (unit test mocks can mask DB constraint issues).
4. **Multi-entity workflows** — realistic sequences: create parent → add children → configure → publish → verify object graph consistent. Catches ordering bugs and transaction boundary issues.
5. **Permission enforcement** — call same endpoint as different roles (CLIENT_ADMIN, PARTNER_SELLER, etc.). Verify access granted/denied correctly with real security context.
6. **Event publishing** — if feature publishes Kafka events, verify correct events emitted with right payload after each triggering operation.
7. **Tenant isolation** — create as Tenant A, query as Tenant B → verify complete isolation (404, not empty list).
8. **Contract conformance** — for each endpoint group, verify response body shape and status codes match the OpenAPI contract. One test class per endpoint group using OpenAPI validator wired to `tenxengage-contracts/`. These go in `test-plan.md` under "Contract Conformance" — NOT in individual story files.

Each scenario goes into the spec's Integration Tests table with: test class, scenario description, expected outcome.

### 2. Fixture gap analysis

- Check existing fixtures: `ls tenxengage-backend/src/test/java/com/tenxengage/app/testdata/`
- If feature introduces new entities, plan new `{Entity}Fixtures.java` files following the builder-return pattern.
- Note any new fixture files needed — `/create-stories` will include them in the F3 foundation task.

### 3. FE E2E coverage note

E2E test scenarios are generated by `/create-stories` per-story. This step's analysis informs the spec's Acceptance Tests pointer and the integration test table only — do NOT write E2E scenarios into spec.md.
