Overview

tenXengage Claude Development & QA Guide

For a single feature, every feature starts as a spec — a single document that both frontend and backend teams use as their source of truth. For initiative-scoped BRDs spanning multiple features, run /decompose-brd first to slice the BRD into a feature roadmap, then run /create-spec {roadmap-slug} F-NN for each slice. The spec lives in tenxengage-blueprint, shared across all teams. API contracts are generated from the spec into tenxengage-contracts, enabling parallel development. Quality gates run before PRs to catch issues early.

Local Configuration (One-time Setup)

Each team member must complete these steps once before using the workflow skills and bug tools. The CLI skills (/bug-reporter, /bug-fixer) read credentials from Claude's environment; the in-app bug reporter reads them from the frontend .env.local file.

Install the Superpowers plugin

Run once per machine in any Claude Code session. This plugin provides the development workflow process skills — brainstorming, writing plans, test-driven development, systematic debugging, code review flows, and more. These power the --tdd flag, the review steps in /ready-check, and the spec-writing flow used by the project commands.

Feature Workflow

Large Features & Progressive Development

Choose the right entry point based on the scope of your input.

Initiative-scoped BRD (multi-feature)

Use when the input covers multiple features, personas, or phases — e.g. a full platform initiative or a product area BRD.

  • • Run /decompose-brd first to slice into feature roadmap + digest
  • • Then run /create-spec {roadmap-slug} F-NN for each slice
  • • Digest is auto-loaded — no copy-paste needed
  • • Feature branches inherit full BRD context from the roadmap branch

Single Feature (standard path)

Use when the input is already a well-scoped single feature — a prompt, a PRD, or a single-feature BRD.

  • • Go straight to /create-spec "description" or /create-spec /path/to/prd.md
  • • Skip /decompose-brd entirely
  • • Each task is self-contained: implement, test, commit
  • • Labeled [BE] or [FE] so each team knows their tasks
0

Decompose BRD — skip for single-feature work

Run in tenxengage-blueprint/ · Initiative-scoped BRDs only

# Slice an initiative BRD into a feature roadmap
/decompose-brd /path/to/initiative-brd.pdf
/decompose-brd /path/to/initiative-brd.md

Use this step when the input is an initiative BRD spanning multiple features, personas, or phases. /decompose-brd slices it into a feature roadmap and writes a digest of cross-cutting context. Skip this step entirely for single-feature work — go straight to Step 1.

File Purpose
roadmaps/{roadmap-slug}/digest.mdBusiness truth — personas, platform constraints, cross-cutting rules; auto-loaded by /create-spec {roadmap-slug} F-NN
roadmaps/{roadmap-slug}/digest-annex.mdAdvisory technical artifacts (auth flows, data model sketches, UI wireframe notes)
roadmaps/{roadmap-slug}/roadmap.mdThin index: feature slices, dependencies, ADR blockers, recommended sequence
roadmaps/{roadmap-slug}/features/F-NN-{roadmap-slug}.mdPer-feature brief; read by /create-spec {roadmap-slug} F-NN automatically
roadmaps/{roadmap-slug}/backlog-seeds.csvStory candidates per feature — input to /seed-clickup (optional)
Branch note: /decompose-brd creates and commits to a dedicated roadmaps/{roadmap-slug} branch. Each subsequent /create-spec {roadmap-slug} F-NN run cuts the feature branch from that roadmap branch, inheriting the digest automatically.

Seed ClickUp — optional, run after /decompose-brd

Run in tenxengage-blueprint/

/seed-clickup

Reads backlog-seeds.csv and creates an Epic (the roadmap) → Milestone (per feature) → Task (per story candidate) hierarchy in ClickUp. Idempotent — already-created items are verified and skipped, so it is safe to re-run at any time.

Requires CLICKUP_API_TOKEN. Prompts for CLICKUP_BACKLOG_LIST_ID on first run and offers to save it to ~/.claude/settings.json.

Note: CLICKUP_BACKLOG_LIST_ID is the ClickUp list for your project backlog — separate from CLICKUP_BUGS_LIST_ID (the bugs list). See Local Configuration to pre-configure it.
1

Create the Spec

Run in tenxengage-blueprint/ · Anyone on the team

# From a roadmap slice (after /decompose-brd) — {roadmap-slug} is the BRD slug from /decompose-brd
/create-spec {roadmap-slug} F-NN

# From a prompt
/create-spec "Quiz engine with timed quizzes, scoring, and certificates"

# From a PRD or BRD file
/create-spec /path/to/prd.md
/create-spec /path/to/feature-brd.pdf
When using the {roadmap-slug} F-NN form, Claude reads roadmaps/{roadmap-slug}/digest.md and roadmaps/{roadmap-slug}/features/F-NN-{roadmap-slug}.md automatically — no copy-paste needed. The feature branch is cut from the roadmaps/{roadmap-slug} branch so it inherits the full BRD context.

Claude reads the requirements, then automatically reads PROJECT-CONTEXT.md, PROJECT-CONTEXT.md from every sibling repo, and relevant docs/patterns/ files to ground the spec in actual project standards.

Scope Analysis

If the requirement is large, Claude decomposes it into sub-requirements and asks whether to create one spec or separate specs per domain.

Plan Mode

Runs in plan mode. You review the outline, request changes, then approve. Claude asks clarifying questions interactively if ambiguities exist.

15-Check Review

After approval, Claude runs a 15-check architectural review covering consistency, security, edge cases, performance, compliance, and more.

The spec covers: data model, API endpoints, DTOs, service methods, frontend pages/components, workflow states, edge cases, test scenarios, and implementation tasks. Each section is labeled [BE], [FE], or [BE + FE].

Implement in Parallel

Backend + Frontend developers, each in their own repo

Phase A: Foundation Tasks (Backend only · sequential)

Run one task per session. Each task must be approved and merged before the next begins.

# Run one task at a time, specifying the task ID
/execute-foundation quiz-engine F1
/execute-foundation quiz-engine F2
...and so on through F5

# With TDD discipline enabled
/execute-foundation quiz-engine F1 --tdd
Task What it does
F1Enums (Java enum classes + DB enum types)
F2Database migration (Flyway schema DDL)
F3JPA entities, repositories, and test fixtures (with tenant isolation)
F4Permission + feature flag seeds (Flyway seed SQL migration)
F5BE-only infrastructure plumbing (Kafka consumers/producers, etc.) — omitted if not applicable
How it works: The skill claims the tracker row, creates a local-only sub-branch, implements the task, runs tests, then pauses for your approval. On approval, it squash-merges into the feature branch and flips the tracker to done. No GitHub PR for individual foundation tasks.
--tdd flag: Activates four superpowers skills — superpowers:test-driven-development before implementation, superpowers:systematic-debugging when tests fail, superpowers:verification-before-completion before the approval pause, and superpowers:requesting-code-review at the approval pause. Without the flag, no TDD discipline is imposed — neither Red → Green → Refactor nor the skill invocations apply.

Phase B: User Stories (BE + FE · parallel where independent)

Check what's eligible, then implement one story per session.

# Check what's ready to pick up (read-only, run from blueprint repo)
/next-eligible quiz-engine

# Implement one story (lean mode)
/load-story quiz-engine US-01

# With TDD discipline enabled
/load-story quiz-engine US-01 --tdd

What /load-story does

  1. 1. Claims the tracker BE or FE cell
  2. 2. Creates a local-only sub-branch
  3. 3. Implements all tasks in the story
  4. 4. Runs tests (Vitest + Playwright for FE; Gradle for BE)
  5. 5. Pauses for your approval
  6. 6. Squash-merges into the feature branch
  7. 7. Flips the tracker cell to done

FE scaffold-and-wait model

If the BE cell for a story isn't done yet:

  • • FE scaffolds components + Vitest tests against contract mocks
  • • Sub-branch stays local (not merged)
  • • Re-invoke /load-story after BE is done to run Playwright against the real BE and finish the merge
Parallelism: Stories that touch disjoint entities can run concurrently in separate sessions. The stories.md dependency graph and /next-eligible output show which stories are safe to parallelize. FE sessions can start immediately after contracts are generated — no need to wait for foundation.

Run from tenxengage-blueprint/ · Never touches code.

# Interactive — prompts for description
/bug-reporter

# One-shot — files a ClickUp ticket immediately
/bug-reporter "Login button unresponsive after token expiry"

# Auto-capture from open browser → evidence folder named bug-<id>

# Escalate evidence folder → ClickUp ticket
/bug-reporter --from-evidence <id>
Mode What you do What you get
Inline textDescribe the bug in plain textClickUp ticket filed immediately
--captureRun while bug is visible in ChromeEvidence folder with screenshots, console errors, network calls
--from-evidence <id>Escalate a previously captured folder by its bug-<id>ClickUp ticket + evidence folder updated with ticket reference

What gets captured automatically with --capture

• Full-page and viewport screenshots
• Current URL, page title, React Router route
• Last 100 console.error / warn entries
• Logged-in user (email, ID, roles, tenant)
• Last 50 network requests (method, URL, status)
• Active feature flags, app build SHA, browser info
MCP setup required for --capture: See Local Configuration → Step 5 for the full Chrome MCP setup. Chrome must be running on port 9222 before the Claude Code session starts. Playwright MCP is a fallback with no logged-in session.
Evidence folder naming: Folders are named bug-<8hexchars> (e.g., bug-a3f2b1c2) — a random ID, never derived from the description. Open bugs-evidence/index.html to browse all captured bugs. Use the <id> (e.g., a3f2b1c2) when passing --from-evidence or --evidence.

In-App Bug Reporter (Frontend Dev Mode)

A floating widget embedded directly in the frontend dev server. Always available during npm run dev — no MCP setup, no Chrome flags, no separate tool.

How to open

  • • Click the 🐞 button fixed to the bottom-right of the app
  • • Keyboard: Cmd+Shift+B (Mac) / Ctrl+Shift+B (Win/Linux)
  • • Esc to close · Cmd+Enter (Mac) / Ctrl+Enter (Win/Linux) to submit

Session recording mode

Open modal → Start session recording → modal closes, 🐞 shows a red pulsing dot. Navigate and reproduce the bug. Click 🐞 again → describe → Stop & Capture Bug. Network and console entries are scoped from the recording start — clean signal, no pre-existing noise.

What gets captured automatically before the modal opens

• Full-page and viewport screenshots
• Current URL, page title, React Router route pattern
• Last 50 network requests (method, URL, status, response snippet)
• Logged-in user — email, ID, name, roles, tenant, feature flags
• Console error and warn entries from current session
• Build SHA, app version, environment, browser, viewport size

High-frequency polling endpoints (e.g. /notifications/unread-count) are suppressed from network capture unless they fail.

Troubleshooting

Symptom Fix
Bug button not visibleOnly shown in dev mode (npm run dev). Not visible in npm run build previews.
"Capture failed" errorCheck the Vite dev server terminal for the actual error. Common causes: blueprint path not found, screenshot timeout.
ClickUp ticket not createdCheck .env.local has BUG_REPORTER_AUTO_TICKET=true and valid token/list ID. Restart the dev server after changes. Check Vite terminal for [vite-plugin-bug-capture] error logs.
Screenshots blank or blackSome pages with complex CSS or WebGL content may not render correctly in html2canvas. The evidence folder is still created without screenshots.
User context empty in meta.mdThe app must be logged in when capture happens. The reporter reads from TanStack Query cache — if the ['auth','me'] query hasn't resolved, user fields are omitted.
Evidence folder missingCheck tenxengage-blueprint/bugs-evidence/ exists. Run: mkdir -p ../tenxengage-blueprint/bugs-evidence from the frontend root.
/bug-reporter --capture falls back to interactive modeMCP server isn't connected. Most common cause: Chrome wasn't running on port 9222 when the Claude Code session started. Start Chrome with --remote-debugging-port=9222 --user-data-dir=/tmp/chrome-debug, then reload the VSCode window.
MCP config changed but capture still not workingMCP servers connect at session start only — reload the VSCode window (Cmd+Shift+P → Reload Window) after any ~/.claude.json change.
MCP capture works but user: fields are empty in meta.mdUsing Playwright MCP (fresh session). Log in to the app in the Playwright browser window before triggering capture, or switch to Chrome DevTools MCP (Option 1) which uses your existing logged-in session.

Bug Fixing

Full end-to-end loop: reproduce → failing test → fix → ready-check → MRs → learnings.

# Scan pending evidence folders, then oldest ClickUp bug
/bug-fixer

# Fix a specific ClickUp task (M3 tracked)
/bug-fixer <clickup-task-id>

# Fix from a captured evidence folder
/bug-fixer --evidence <slug>

# Quick inline fix on current branch, no MR (M1)
/bug-fixer --inline "description"

# Fix on dedicated branch, no ClickUp ticket (M2)
/bug-fixer --standalone "description"

# Close without fixing
/bug-fixer --wont-fix <slug-or-id> "reason"
Mode When to use Branch MRs ClickUp
M1 InlineQuick fix on current feature branchNo new branchNoNo
M2 StandaloneFix without a ClickUp ticketbug/<id>YesNo
M3 TrackedFix a filed ClickUp ticketbug/clickup-<clickup-id>-<id>YesYes

Fix loop — step by step

  1. 1. Normalize — reads ticket / evidence / inline text; prints a starting hypothesis and data path; waits for your go
  2. 2. Duplicate detection — searches evidence folders, bugs-index, and ClickUp for similar bugs
  3. 3. Reproduce — explores the critical path; forms explicit hypotheses before reading each file
  4. 4. Write failing test — JUnit (BE), Vitest (FE), or Playwright E2E; confirms the test fails at an assertion (not a typo / setup error) and matches the reported symptom
  5. 5. Implement fix — cause is already pinned by the critical path (Step 1) and the failing test (Step 4); no workarounds; if 3+ fix attempts fail, stops and re-examines the path/hypothesis instead of attempting fix #4
  6. 6. Ready-check — runs /ready-check in each affected repo; no MR until green
  7. 7. Verification gate — runs superpowers:verification-before-completion
  8. 8. Visual re-confirmation — Playwright captures before/after if screenshots were in evidence
  9. 9. Create MRs — one per affected repo; ClickUp status → needs-review
  10. 10. Learnings — promotes cross-cutting lessons to docs/patterns/ or docs/learnings.md
  11. 11. bugs-index.md — appends one line to the append-only corpus
  12. 12. Final report — printed to screen; evidence folder updated

Dev's current checkout is never touched — all work happens in /tmp/ worktrees (except M1).

Configuring the Base Branch

By default, every feature branch is cut from main. Set FEATURE_BASE_BRANCH in your Claude settings to change this — globally or per-repo.

Global (all repos) — ~/.claude/settings.json

{
  "env": {
    "FEATURE_BASE_BRANCH": "develop"
  }
}

Per-repo override — {repo}/.claude/settings.json

{
  "env": {
    "FEATURE_BASE_BRANCH": "release/2.0"
  }
}

The variable is read at runtime by every skill that creates a feature branch. If unset, skills fall back to main.

FAQ

I have a large initiative BRD covering multiple features

Run /decompose-brd /path/to/brd.pdf in the blueprint repo. It slices the BRD into a feature roadmap (roadmaps/{roadmap-slug}/roadmap.md) and writes a digest of cross-cutting context. Each feature slice is listed with a /create-spec {roadmap-slug} F-NN invocation you can run directly — no copy-paste needed.

The adversarial review step fails saying Codex is unavailable

Codex CLI is not authenticated. Run codex login in your terminal (uses your ChatGPT/OpenAI account) or add OPENAI_API_KEY to the env block in ~/.claude/settings.json. See Step 6 — Set up Codex in the Local Configuration section for full instructions.

I'm doing a bug fix with no spec. How do I run ready-check? ›
Provide none as the feature ID when prompted. Stages like Contract Compliance will be marked NOT_APPLICABLE.
I need to change the spec after implementation started. What do I do? ›
Edit the spec in the blueprint repo, run /review-spec to re-validate, and re-generate contracts if the API changed.
I want maximum TDD discipline. How do I enable it? ›
Pass --tdd to /execute-foundation or /load-story. This enables four superpowers skills: superpowers:test-driven-development before implementation, superpowers:systematic-debugging when tests fail, superpowers:verification-before-completion before the approval pause, and superpowers:requesting-code-review at the approval pause. Without the flag, no TDD discipline is imposed — neither Red → Green → Refactor nor the skill invocations apply.
My team branches features from develop instead of main. How do I configure that? ›
Set FEATURE_BASE_BRANCH in your Claude settings. Add "FEATURE_BASE_BRANCH": "develop" to the env section of ~/.claude/settings.json to apply it globally across all repos, or to a specific repo's .claude/settings.json to override just that repo. All feature-branching skills read this variable at runtime and fall back to main if it is not set. See the Configuring the Base Branch section for full details.
The foundation tasks aren't done but I want to start FE work. Is that OK? ›
Yes. FE story sessions can start immediately after contracts are generated. Scaffold against the generated types and mock the API; wire to real BE endpoints as foundation completes. Foundation must finish before any BE story session starts (BE stories depend on the entities and permissions foundation creates).
What story should I work on next? ›
Run /next-eligible in the blueprint repo. It reads the tracker and prints a punch list — foundation tasks and story layers that are unblocked, plus what's still blocked and why. Read-only; never modifies anything.
The adversarial review failed. What now? ›
The step blocks on critical or high severity findings with confidence ≥ 0.70. The output lists each blocking issue with its file, line range, risk, and recommended fix. Fix the issues, then re-run just that step: /ready-check adversarial-review.
I want to run just the tests, not the full ready-check. ›
Use /run-tests — it runs tests scoped to your changes and updates the ready-check report. Or use /ready-check tests to target just the test stage.
I have a PRD or BRD document instead of typing out the requirement. ›
Pass the file path directly: /create-spec /path/to/document.pdf. Claude reads it, summarizes the requirements, and confirms with you before generating the spec.
I want to capture a bug visually before filing a ticket. ›
Run /bug-reporter --capture while the bug is visible in your browser. This creates an evidence folder in bugs-evidence/bug-<id>/ (e.g., bug-a3f2b1c2) with screenshots, console logs, and network data. Open bugs-evidence/index.html to browse. File the ClickUp ticket later with --from-evidence <id>.
--capture says MCP is unavailable. ›
Chrome must be running with --remote-debugging-port=9222 before the Claude Code session starts. Start Chrome with that flag, then reload the VSCode window (Cmd+Shift+P → Reload Window on Mac, Ctrl+Shift+P → Reload Window on Windows/Linux). See the Bug Reporting section for the full setup.
A bug fix touches both backend and frontend. Does bug-fixer handle that? ›
Yes. /bug-fixer creates one branch and one worktree per affected repo (/tmp/bugfix-<slug>-backend/, /tmp/bugfix-<slug>-frontend/), runs /ready-check in each, and creates one MR per repo on the same shared branch name. Your current checkout in either repo is never touched.
I want to create mockups for FE stories before implementing them. ›
Run /create-mockups from the frontend repo after /create-stories has been run. The skill proposes a screen grouping, waits for your confirmation, then generates per-screen TSX mockups plus a FullFeatureMockup.tsx feature navigator. Routes are auto-served by MockupRouter — no App.tsx edits needed. Open localhost:5173/mockup/ to see the feature navigator with a floating pill to switch between all screens, or go directly to localhost:5173/mockup//{screen-slug} for a specific screen. Mockup routes are dev-only and excluded from production builds — guarded by import.meta.env.DEV and tree-shaken by Vite. Review mockups in Chrome using the Claude extension, iterate until satisfied, then proceed to implementation — /load-story will automatically pick up the mockup paths. Mockups are always optional.
I want to report a bug quickly without setting up MCP or Chrome flags. ›
Use the In-App Bug Reporter — click the 🐞 button in the bottom-right of the app while npm run dev is running, or press Cmd+Shift+B (Mac) / Ctrl+Shift+B (Win/Linux). It captures screenshots, console errors, and network calls automatically before the modal opens. No MCP, no Chrome flags, no separate tool required.
I forgot to create a spec and already started coding. ›
That's fine. You can create the spec retroactively, or run /ready-check with feature ID none.
