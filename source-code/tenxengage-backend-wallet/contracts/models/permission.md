# Permission Model

Defines the global permission catalog. Permissions are the atomic unit of access control in the 5-layer permission hierarchy.

## Entity: Permission

| Field          | Type     | Required | Constraints           | Notes                                          |
| -------------- | -------- | -------- | --------------------- | ---------------------------------------------- |
| id             | UUID     | yes      | primary key           | Generated by database                          |
| permissionKey  | string   | yes      | unique, max 100       | Identifier (e.g. "action.incentive.view")      |
| displayName    | string   | yes      | max 150               | Human-readable name                            |
| description    | string   | no       | TEXT                  | What this permission controls                  |
| category       | string   | yes      | max 50                | Grouping category (e.g. "Incentives", "Users") |
| permissionType | string   | yes      | max 20                | Type classification                            |
| scope          | string   | yes      | max 20, default "ALL" | INTERNAL, EXTERNAL, ALL, or PLATFORM           |
| sortOrder      | integer  | yes      | default 0             | Display ordering within category               |
| createdAt      | datetime | yes      | —                     | ISO 8601                                       |
| updatedAt      | datetime | yes      | —                     | ISO 8601                                       |

## Permission Key Format

All permissions follow: `action.<resource>.<operation>`

Examples:

- `action.incentive.view`, `action.incentive.create`, `action.incentive.edit`
- `action.users.view`, `action.users.create`, `action.users.delete`
- `action.claim.view`, `action.claim.submit`, `action.claim.unclaim`
- `action.tenx.clients.view`, `action.tenx.clients.manage` (platform-level)

## Scope Values

| Scope    | Description                                                           |
| -------- | --------------------------------------------------------------------- |
| INTERNAL | Only available to client-side roles (CLIENT_ADMIN, ACTIVITY_APPROVER) |
| EXTERNAL | Only available to partner-side roles (PARTNER_ADMIN, PARTNER_SELLER)  |
| ALL      | Available to both internal and external roles                         |
| PLATFORM | Only available to TENX_ADMIN (platform super-admin)                   |

## 5-Layer Permission Hierarchy

Effective permissions are resolved top-down. Each layer can grant or revoke:

1. **Platform defaults** — Permission catalog defines the base set
2. **Tenant grants** (ClientPermissionGrant) — Client-level enable/disable
3. **Role permissions** (ClientRolePermission) — Role-level grants
4. **Company overrides** (CompanyPermissionOverride) — Per-partner-company overrides
5. **User overrides** (UserPermissionOverride) — Per-user overrides

Resolution: A permission is effective if it is granted at every applicable layer. Lower layers can only further restrict, not expand beyond what the layer above allows.

## Notes

- The permission catalog is global (not tenant-scoped)
- 124 permissions are seeded at system initialization
- Permissions are referenced by `permissionKey` string throughout the system
