# RewardTransaction Model

Records a single reward credit (currently always `earned`) tied to a claim approval. The `reward_transactions` row is written by the backend when a claim is approved with a reward currency. There is no spend / redemption side yet — every row is `type: "earned"` for now. The `type` field is reserved on the response shape so the future redemption feature can fill in `"spent"` rows without changing the contract.

| Field              | Type     | Required | Constraints              | Notes                                                    |
| ------------------ | -------- | -------- | ------------------------ | -------------------------------------------------------- |
| id                 | UUID     | yes      | primary key              | Generated by database                                    |
| clientId           | UUID     | yes      | foreign key              | References Client (tenant)                               |
| userId             | UUID     | yes      | foreign key              | References User                                          |
| incentiveId        | UUID     | yes      | foreign key              | References Incentive that paid this reward               |
| currencyId         | string   | yes      | max 50                   | Currency identifier (e.g. "cash", "points")              |
| amountPotential    | decimal  | yes      | precision 15, scale 2    | What the rule would have paid                            |
| amountAwarded      | decimal  | yes      | precision 15, scale 2    | What was actually paid (after budget caps)               |
| budgetCapped       | boolean  | yes      | default false            | Whether the amount was reduced by a budget cap           |
| claimActionId      | UUID     | no       | foreign key              | References ClaimAction (the source claim)                |
| completionId       | UUID     | no       | foreign key              | References Completion (for completion-based incentives)  |
| createdAt          | datetime | yes      | —                        | ISO 8601                                                 |
| updatedAt          | datetime | yes      | —                        | ISO 8601                                                 |

## Response Shape

The `RewardTransactionResponse` DTO returned by `/api/v1/reward-transactions` shapes the row for the UI:

| Field                | Type     | Notes                                                                            |
| -------------------- | -------- | -------------------------------------------------------------------------------- |
| id                   | UUID     | Transaction id                                                                   |
| date                 | datetime | `createdAt` of the transaction (ISO 8601)                                        |
| type                 | string   | `"earned"` or `"spent"`. Always `"earned"` today; `"spent"` reserved for future. |
| currencyId           | string   | Currency identifier                                                              |
| amount               | string   | Awarded amount, plain string (no scientific notation)                            |
| incentiveId          | UUID     | Source incentive                                                                 |
| incentiveName        | string   | Display name of the source incentive (joined at query time)                      |
| claimActionId        | UUID?    | Source claim action (null for non-claim-driven credits)                          |
| purchaseOrderNumber  | string?  | Order number of the related PO, if a `claimActionId` is set                      |

## Multi-Tenancy

- Tenant-scoped via `client_id`. The `tenantFilter` Hibernate filter applies automatically.

## Notes

- Rows are only ever inserted by `ClaimService.createRewardTransaction` when a claim is approved with a reward currency. There is no controller-level write path.
- Reads are paginated and ordered by `createdAt DESC`.
- Date-range filters apply to `createdAt`.
- Spend / redemption is not modelled yet. When it is added, those rows will share this table (with a new `type` column or a sibling table) — the response DTO already exposes `type` so the UI scaffolding for "Spent" rows is forward-compatible.
