# BalanceExpirationPolicy Model

Per-currency, opt-in policy defining when unused reward balances expire for a tenant
(reward-balance-expiration / F-09). One row per `(client_id, currency_id)`. Expiration is **off
by default**; there is no platform default policy — a Client Admin must explicitly enable it.

Tenant-isolated via Hibernate `@Filter(tenantFilter)` (request-path reads only — the scheduled
batch binds `client_id` explicitly per wallet). Soft-deleted; optimistic-locked via `@Version`.

| Field      | Reason                                          |
|------------|-------------------------------------------------|
| `clientId` | Tenant isolation — resolved server-side         |

The API response (`BalanceExpirationPolicyResponse`) addresses a policy by `currencyId` and does
**not** surface the surrogate `id` (policies are upsert-by-currency; no cross-tenant ID lookups).

## API DTOs

### UpsertBalanceExpirationPolicyRequest

`PUT /api/v1/redemption/expiration/policies/{currencyId}`. Structural validation only at the API
layer (`enabled`, `expirationMode`, `leadTimeDays` are `@NotNull`). Cross-field and bounds rules
(FR-09.9) are enforced in the service and surface as **422** with a specific `errorCode`.

| Field | Type | Required | Notes |
|---|---|---|---|
| `enabled` | boolean | yes | Toggle expiration for this currency type |
| `expirationMode` | ExpirationMode | yes | `INACTIVITY` \| `FIXED_DATE` |
| `inactivityDays` | integer | no | Required when `INACTIVITY`; bounds [30, 1825]; null when `FIXED_DATE` |
| `fixedExpiryDate` | date | no | Required when `FIXED_DATE`, future-only; null when `INACTIVITY` |
| `leadTimeDays` | integer | yes | `>= 1`; `< inactivityDays` when `INACTIVITY` |

### BalanceExpirationPolicyResponse

`from(BalanceExpirationPolicy)`.

| Field | Type | Notes |
|---|---|---|
| `currencyId` | String | Currency code this policy governs |
| `currencyDisplayName` | String | Human-readable label (fallback; FE source of truth is `config/currencies.ts`) |
| `enabled` | boolean | Whether expiration is active |
| `expirationMode` | ExpirationMode | `INACTIVITY` \| `FIXED_DATE` |
| `inactivityDays` | Integer | Present when `INACTIVITY` |
| `fixedExpiryDate` | LocalDate | Present when `FIXED_DATE` |
| `leadTimeDays` | Integer | Advance-notice lead time |
| `enabledAt` | Instant | "Active since" caption; null when never enabled |
| `updatedAt` | Instant | "Last changed" caption |

## Validation Rules (service layer → 422, `errorCode`)

- `expirationMode = INACTIVITY` ⇒ `inactivityDays` required, within `[30, 1825]`; `fixedExpiryDate` must be null.
- `expirationMode = FIXED_DATE` ⇒ `fixedExpiryDate` required and strictly in the future (tenant date); `inactivityDays` must be null.
- `leadTimeDays >= 1`; when `INACTIVITY`, `leadTimeDays < inactivityDays`.
- `currencyId` (path) must be a recognised currency type — unknown ⇒ 422.

## Business Rules

- **Opt-in, no default** — cash never expires unless an enabled cash policy exists (FR-09.2 / FR-09.3).
- **Enable / material change** sets `enabledAt`, which anchors the grace window — nothing expires until at least one full `leadTimeDays` window has elapsed since `enabledAt` (no retroactive expiry, FR-09.7).
- **Disable or relax** (lengthen inactivity / push fixed date / lengthen lead) cancels not-yet-executed (already-notified) expirations and re-notifies affected partners (FR-09.10); relaxing also resets `enabledAt`, restarting the grace window.
- Concurrent admin edits are guarded by `@Version` → **409** on conflict.

## Relationships

- One per `(client_id, currency_id)` — `UNIQUE (client_id, currency_id)`
- `@OneToMany` → `BalanceExpiryNotice` (mappedBy `policy`) — see [balance-expiry-notice.md](balance-expiry-notice.md)

## Data Retention

Soft-deleted; retained 7 years for governance/audit of expiry policy history.
