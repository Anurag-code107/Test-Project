# BalanceExpiryNotice Model

Tracks one scheduled expiry event for one wallet + currency (reward-balance-expiration / F-09).
Enforces once-only advance notice (FR-09.4), idempotent expiry (FR-09.8), and
re-notify-on-cancel (FR-09.10). Written and advanced by the scheduled SYSTEM batch; it is an
**internal operational entity and is not exposed directly through any API** (the aggregate
preview and breakage report never surface a `walletId`).

Tenant-isolated via Hibernate `@Filter(tenantFilter)` on the request path; the scheduler binds
`client_id` explicitly per wallet (no ambient `TenantContext`). Soft-deleted (notices are
retained as the evidentiary trail of advance notice); optimistic-locked via `@Version`.

## Fields Never Exposed in API

This entity is internal. No field is surfaced directly. In particular:

| Field      | Reason                                                                 |
|------------|------------------------------------------------------------------------|
| `clientId` | Tenant isolation — resolved server-side / bound per wallet in batch    |
| `walletId` | Per-wallet identity is never surfaced; previews/reports are aggregate-only |
| `deleted`  | Soft-delete flag; internal                                             |
| `version`  | Optimistic lock counter; internal                                      |

## Lifecycle (ExpiryNoticeStatus)

```
SCHEDULED → NOTIFIED   (batch warn phase: balance enters lead window; sends BALANCE_EXPIRING_SOON)
NOTIFIED  → EXPIRED    (batch expire phase: scheduled_expiry_date reached; writes EXPIRY ledger debit, sends BALANCE_EXPIRED)
SCHEDULED → CANCELLED  (policy disable/relax before any notice was sent)
NOTIFIED  → CANCELLED  (policy disable/relax; sends BALANCE_EXPIRY_CANCELLED to already-notified partners — FR-09.10)
```

`EXPIRED` and `CANCELLED` are terminal. A new `SCHEDULED` notice may be created if a policy is
re-enabled later.

## Idempotency

`UNIQUE (wallet_id, currency_id, scheduled_expiry_date)` is the idempotency key (FR-09.8): at
most one notice per wallet + currency + expiry event. Combined with the status guard, a batch
re-run never produces a double-debit. Advance notice is sent only while `notifiedAt IS NULL`;
setting it dedups re-sends across retries (FR-09.4).

## Relationships

- `@ManyToOne` → `BalanceExpirationPolicy` (FK `policy_id`) — see [balance-expiration-policy.md](balance-expiration-policy.md)
- `@ManyToOne` → `RewardWallet` (FK `wallet_id`) — see [reward-wallet.md](reward-wallet.md)
- references `LedgerEntry` (FK `ledger_entry_id`) — the `EXPIRY` debit — see [ledger-entry.md](ledger-entry.md)

## Data Retention

Soft-deleted, retained 7 years — proof of advance notice before an irreversible expiry debit
(FR-09.7). The `EXPIRY` `LedgerEntry` itself is immutable and append-only (never deleted).
